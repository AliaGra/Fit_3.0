Технічне завдання Модуль «План тренувань»

Версія 1.0  |  Лютий 2026
Стек: Node.js · Railway · Supabase · Telegram Bot API
 
1. МЕТА ТА КОНТЕКСТ
Цей документ описує технічне завдання для реалізації модуля «План тренувань» у Telegram-боті FIT 3.0. Модуль охоплює два режими роботи:
•	Індивідуальний план — тренер створює план вручну для конкретного учня
•	Автоматичний план — алгоритм генерує план на основі профілю учня без ручного втручання тренера

Модуль є центральним для ціннісної пропозиції продукту: тренер отримує інструмент ведення учнів, учень — персоналізовану програму з урахуванням медичного стану, цілей та рівня підготовки.

Параметр	Значення
Стек	Node.js + Railway + Supabase (PostgreSQL) + Telegram Bot API
Мова UI	Українська
Архітектура	FSM через Supabase bot_state; callback_data через ENUM constants.js
Бібліотека вправ	exercise_library (Supabase), поле medical_contraindications, safe_for, modifications
Медичний профіль	user_medical_conditions: MC001–MC025 + severity
Пріоритет	🔴 Критично для запуску продукту

3. БАЗА ДАНИХ — SQL МІГРАЦІЇ
⚠️ VETO: Не відхилятись від схеми без окремої міграції. Еталон: Supabase_створення_таблиць_FIT3.sql
3.1 Нова таблиця: user_medical_conditions
Зберігає активні та архівні медичні стани учня. Один запис на стан (UNIQUE chat_id + mc_code).

CREATE TABLE user_medical_conditions (
  id           uuid DEFAULT gen_random_uuid() PRIMARY KEY,
  chat_id      text NOT NULL REFERENCES users(chat_id) ON DELETE CASCADE,
  mc_code      text NOT NULL,       -- MC001...MC025
  severity     text NOT NULL,       -- mild/moderate/severe або специфічне
  notes        text,                -- примітка тренера
  is_active    boolean DEFAULT true,
  created_at   timestamptz DEFAULT now(),
  updated_at   timestamptz,
  UNIQUE (chat_id, mc_code)
);
CREATE INDEX ON user_medical_conditions(chat_id, is_active);

3.2 Нова таблиця: training_plans
CREATE TABLE training_plans (
  plan_id         uuid DEFAULT gen_random_uuid() PRIMARY KEY,
  coach_id        text REFERENCES users(chat_id),
  student_id      text REFERENCES users(chat_id),
  plan_name       text NOT NULL,
  goal            text NOT NULL CHECK (goal IN ('lose','gain','keep')),
  level           text NOT NULL CHECK (level IN ('beginner','intermediate','advanced')),
  split_scheme    text,
  days_per_week   integer,
  description     text,
  is_active       boolean DEFAULT false,
  is_template     boolean DEFAULT false,
  generation_type text DEFAULT 'manual', -- manual | auto | auto_revision | ai
  revision_weeks  integer,              -- дефолт: beginner=10, intermediate=7, advanced=5
  parent_plan_id  uuid REFERENCES training_plans(plan_id),
  created_at      timestamptz DEFAULT now(),
  activated_at    timestamptz,
  valid_until     timestamptz,          -- activated_at + revision_weeks * 7 днів
  revision_reminder_sent_at timestamptz
);

3.3 Нова таблиця: training_plan_exercises
CREATE TABLE training_plan_exercises (
  id               uuid DEFAULT gen_random_uuid() PRIMARY KEY,
  plan_id          uuid NOT NULL REFERENCES training_plans(plan_id) ON DELETE CASCADE,
  exercise_id      integer REFERENCES exercise_library(id),
  exercise_name    text NOT NULL,
  day_number       integer NOT NULL,
  day_label        text,         -- 'Верх тіла', 'Push', 'Full Body'
  order_in_day     integer DEFAULT 1,
  sets             integer,
  reps             text,          -- '10-12', '15', '30 сек'
  rest_sec         integer,
  notes            text,          -- техніка + модифікація при MC
  medical_status   text DEFAULT 'NEUTRAL', -- NEUTRAL|SAFE|ALLOWED_WITH_MOD
  progression_type text DEFAULT 'weight',  -- weight|reps|none
  target_weight    decimal(5,2)
);
CREATE INDEX ON training_plan_exercises(plan_id, day_number);

4. МОДУЛЬ: МЕДИЧНИЙ ПРОФІЛЬ (lib/medicalProfile.js)
4.1 Призначення
CRUD-модуль для управління медичними станами учня. Тренер додає, редагує та видаляє стани. Підтримує 25 кодів (MC001–MC025) та специфічні severity відповідно до документа «Розшифровка severity».

4.2 UI-сценарій для тренера
Крок	Дія тренера	Дія системи
1	Мої учні → [Ім'я] → Медичний профіль	Показ списку активних MC-станів учня з severity. Кнопка [+ Додати стан]
2	[+ Додати стан]	FSM: MC_ADD → показ inline-клавіатури з категоріями: Суглоби / Серце і судини / Хребет / Метаболізм / Жіноче здоров'я / Інше
3	Вибір категорії	FSM: MC_ADD_CODE → показ MC-кодів категорії з назвами (МС001 — Коліна, ...)
4	Вибір MC-коду	FSM: MC_ADD_SEVERITY → показ варіантів severity для вибраного коду
5	Вибір severity	INSERT/UPDATE user_medical_conditions. Підтвердження: «Стан MC001 (mild) додано»
6	Видалити стан	MC_REMOVE:{mc_id} → is_active = false (м'яке видалення, не DELETE)

5. МОДУЛЬ: МЕДИЧНА ФІЛЬТРАЦІЯ (lib/medicalFilter.js)
5.1 Функція filterExerciseForUser(exercise, userMedConditions)
Повертає один із чотирьох статусів для кожної вправи відносно профілю конкретного учня.

Статус	Умова	Дія при генерації плану
BLOCKED	mc_code є у medical_contraindications І user.severity >= threshold	Виключити з плану, замінити alternatives
ALLOWED_WITH_MOD	mc_code є у medical_limitations	Включити з позначкою ⚠️ та notes = modifications[mc_code]
SAFE	mc_code є у safe_for вправи	Пріоритизувати — брати в першу чергу
NEUTRAL	Жодного медичного маркера	Стандартний відбір

5.2 Алгоритм порівняння severity
Порядок severity (від легкого до важкого):
mild < moderate < severe   (для більшості станів)
stage1 < stage2 < stage3   (для MC004 Гіпертонія)
class1 < class2 < class3   (для MC018 Ожиріння)
osteopenia < mild < moderate < severe   (для MC008)
trimester1 < trimester2 < trimester3   (для MC009)
controlled < uncontrolled   (для MC017)
recent → більш обмежений (для MC020, MC023)

⚠️ Реалізація: SEVERITY_ORDER у constants.js як масиви для кожного MC-типу. Порівняння через indexOf().

5.3 Відображення в бібліотеці вправ
У картці вправи (lib/library.js) — деталізований підпис на основі filterExerciseForUser():
•	🚫 Протипоказано — BLOCKED
•	⚠️ З обмеженнями: [текст модифікації] — ALLOWED_WITH_MOD
•	✅ Рекомендовано при вашому стані — SAFE
•	(нічого) — NEUTRAL


 
6. МОДУЛЬ: АВТОМАТИЧНА ГЕНЕРАЦІЯ ПЛАНУ (lib/planGenerator.js)
6.1 Функція generateTrainingPlan(studentChatId, options)
Повна автоматична генерація плану тренувань на основі профілю учня.

generateTrainingPlan(studentChatId, {
  days_per_week: 3,      // optional — бере дефолт якщо не задано
  plan_name: 'Авто',     // optional
  created_by: coach_id,  // або 'auto'
  is_active: false,      // тренер активує вручну
})

6.2 Крок 1 — Читання профілю учня
•	users → goal, gender, weight, height, experience_days
•	user_medical_conditions WHERE is_active = true
•	BMI = weight / (height/100)²
•	level: 0–90 днів → beginner; 91–365 → intermediate; 366+ → advanced

6.3 Крок 2 — Параметри плану
Level	Днів/тиж	Схема (split_scheme)	Розподіл по днях
beginner	2	full_body	Д1: все тіло · Д2: все тіло
beginner	3	full_body	Д1,Д2,Д3: все тіло
intermediate	3	upper_lower_full	Д1: Верх · Д2: Низ · Д3: Повне
intermediate	4	upper_lower_x2	Д1/Д3: Верх · Д2/Д4: Низ
advanced	4	ppl_upper	Push · Pull · Legs · Upper
advanced	5	ppl_upper_lower	Push · Pull · Legs · Upper · Lower

6.4 Крок 3 — Параметри навантаження за ціллю
Goal	Повтори	Підходи	Пріоритет вправ
lose (схуднення)	15–20 повт	3 підходи	Ізоляція > Базова. Коротший відпочинок
gain (набір маси)	6–10 повт	4–5 підходів	Базова > Ізоляція. Важкі компаунди
keep (підтримка)	10–15 повт	3–4 підходи	Баланс Базова/Ізоляція. Різноманітність

6.5 Крок 4 — Кількість вправ на день
Тип дня	Beginner	Intermediate	Advanced
Full Body	5–6 вправ	6–7 вправ	7–8 вправ
Upper / Lower	4–5 вправ	5–6 вправ	6–7 вправ
Push / Pull / Legs	—	5–6 вправ	6–8 вправ

6.6 Крок 5 — Алгоритм підбору вправ для дня
Для кожного тренувального дня (з урахуванням Anti-Repeat Logic):
•	SELECT * FROM exercise_library WHERE group_level2 IN (target_groups) AND active = 'YES'
•	filterExerciseForUser() → виключити BLOCKED, позначити ALLOWED_WITH_MOD
•	Пріоритет SAFE → NEUTRAL; ALLOWED_WITH_MOD включаємо з notes
•	Фільтр по difficulty: beginner → Низька/Середня; advanced → Середня/Висока
•	Фільтр по vid: gain → Базова першочергово; lose → Ізоляція
•	Жінки (gender=female): акцент на Ноги + Сідниці у Low/Full Body
•	MC018 class2/class3: виключити вправи стоячи з вагою, тільки тренажери
•	Anti-Repeat А: виключити exercise_id вже доданих в інші дні плану (та сама group_level2)
•	Anti-Repeat Б: виключити exercise_id з попереднього плану учня (тільки для ізоляції)
•	Зважений рандом: weight = 1 / (usage_count + 1) — нові вправи мають максимальний пріоритет

6.7 Anti-Repeat Logic — правила різноманітності
Три правила що забезпечують варіативність вправ для учня:

Правило	Назва	Що виключається	Виняток
А	Внутрі плану	Вправа не може з'явитись у двох різних днях плану для тієї самої group_level2	Базові для beginner: Full Body допускає повтор, але не більше 2 днів/тиж
Б	Між планами	При ревізії або новій генерації — виключити exercise_id з попереднього плану (тільки ізоляція)	Базові вправи завжди залишаються (техніку потрібно закріплювати)
В	Зважений рандом	weight = 1 / (usage_count + 1). Вправа ніколи не використана → weight=1.0 (макс). Використана 3 рази → weight=0.25	Базові вправи виключені з зваженого рандому

⚠️ Функція getExerciseUsageCount(studentChatId, groupLevel2) — кешувати на час генерації плану, не звертатись до БД для кожної вправи окремо

Якщо після застосування правил А+Б пул став меншим за потрібну кількість вправ → знімати обмеження Б (між планами) і логувати. Правило А (внутрі плану) не знімається ніколи.

6.8 Крок 6 — Запис у БД
•	INSERT INTO training_plans → отримати plan_id
•	Для кожної вправи кожного дня: INSERT INTO training_plan_exercises
•	Поле notes = modifications[mc_code] якщо ALLOWED_WITH_MOD
•	Поле medical_status = NEUTRAL|SAFE|ALLOWED_WITH_MOD
•	valid_until = activated_at + revision_weeks * 7 днів (beginner=10 тиж, intermediate=7, advanced=5)

8. ВИКОНАННЯ ПЛАНУ УЧНЕМ (lib/training.js)
8.1 UI-сценарій — учень
Крок	Дія учня	Дія системи

8.2 Тренер — тренування учня з планом
При виборі учня з активним планом:
•	showCoachTrainingPlanChoice → вибір: [День 1 плану] / [День 2 плану] / ... / [Вільне тренування]
•	COACH_PLAN_DAY:{day_number} → запуск плану дня
•	COACH_TRAIN_FREE → стандартне вільне тренування

8.3 Автопрогресія
Тип прогресії	Умова	Дія системи
Вагова (weight)	Виконав всі підходи на всі повтори	+2.5 кг (базові) або +1.25 кг (ізоляція)
Повторна (reps)	Завершив верхню межу діапазону	+1–2 повтори або перехід до вагової
Деавтоматизація	Не виконав мінімум 2 рази поспіль	−10% ваги + сповіщення тренеру

8.4 Обмеження прогресії при MC
•	ALLOWED_WITH_MOD: прогресія тільки через reps, не через weight
•	severity = moderate: ліміт ваги = поточна вага × 1.5
•	Зміна severity → перевірка всіх вправ плану через filterExerciseForUser()
•	Нова BLOCKED вправа → замінити на alternatives або деактивувати
•	Логувати зміну у таблицю plan_adjustments


 
9. ЛОГІКА РЕВІЗІЇ ПЛАНУ
9.1 Три рівні змін плану
Ревізія — це не просто нагадування. Система розрізняє три рівні змін:

Рівень	Назва	Що змінюється	Тригер
Рівень 1	Мікро-корректировка	Автопрогресія: вага +2.5 кг або повтори +1–2. Схема і вправи незмінні.	Автоматично після кожного тренування
Рівень 2	Ротація вправ	Та сама схема і групи м'язів. Замінюється 30–50% вправ. Базові (присідання, жим, тяга) НЕ міняються — тільки ізоляція.	Планова ревізія по revision_weeks
Рівень 3	Зміна схеми	Нова сплітова схема: Full Body → Upper/Lower, PPL → 4-day split. Кардинальний перегляд об'єму і акцентів.	Раз на 3–6 міс або зміна goal/level

⚠️ Рівень 1 — автоматично кожне тренування. Рівень 2 — ревізія по розкладу. Рівень 3 — тільки вручну тренером або при зміні goal/level.

9.2 Дефолтні терміни ревізії за рівнем (revision_weeks)

Рівень учня	revision_weeks	Обґрунтування
beginner (0–3 міс)	10 тижнів	Новачок прогресує довго — нейром'язова адаптація ще не завершена. Змінювати рано шкідливо: тіло не закріплює паттерн руху.
intermediate (3–12 міс)	7 тижнів	Тіло адаптується швидше, плато настає раніше. Потрібна регулярна ротація вправ.
advanced (1+ рік)	5 тижнів	Досвідчене тіло адаптується дуже швидко. Потрібна постійна варіативність для продовження прогресу.

9.3 Два режими роботи
Режим з тренером (generation_type = 'manual')
•	Тренер задає revision_weeks вручну при створенні плану (дефолт підставляється автоматично за рівнем)
•	По закінченню valid_until: тренер отримує сповіщення і вручну виконує Рівень 2 або Рівень 3
•	Функція: getPlansDueForRevision() → markPlanRevisionReminderSent()

Авто-режим без тренера (generation_type = 'auto')
•	revision_weeks береться з дефолтів п. 9.2 автоматично
•	По закінченню valid_until: система сама генерує новий план через generatePlanRevision() — Рівень 2
•	Базові вправи НЕ замінюються. Замінюється 30–50% ізоляції
•	target_weight для нових вправ = NULL (учень починає з нуля для нової вправи)
•	Старий план архівується (is_active = false), новий активується автоматично
•	Учень отримує: Твій план оновлено! Ось нові вправи на наступні N тижнів 💪

9.4 Алгоритм generatePlanRevision(plan_id)
Виконується автоматично по cron або вручну тренером:
•	1. Читаємо training_plan_exercises поточного плану
•	2. Розділяємо: базові (vid='Базова') та ізоляційні (vid='Ізоляція')
•	3. Базові — залишаємо без змін (exercise_id, sets, reps, target_weight)
•	4. З ізоляційних — обираємо 30–50% для заміни (пріоритет: вправи де прогресія зупинилась 2+ тренування)
•	5. Для кожної на заміну: SELECT з exercise_library (та сама group_level2, id != поточний) → filterExerciseForUser()
•	6. Замінюємо вправи: зберігаємо day_number, order_in_day, sets, reps; target_weight = NULL
•	7. INSERT новий training_plans (generation_type='auto_revision', parent_plan_id = старий)
•	8. INSERT нові training_plan_exercises
•	9. Активуємо новий план, архівуємо старий; логуємо в plan_adjustments

9.5 Endpoint ревізії (lib/planRevisionReminders.js)
Endpoint: GET /cron/plan-revision
Тригер: valid_until <= now AND revision_reminder_sent_at IS NULL

•	Режим manual: getPlansDueForRevision() → сповіщення тренеру → markPlanRevisionReminderSent()
•	Режим auto: getPlansDueForRevision() → generatePlanRevision() → активація нового плану → сповіщення учню
⚠️ valid_until = activated_at + revision_weeks * INTERVAL '7 days'. Поля схеми — розд. 3.2


11. VETO RULES — ОБОВ'ЯЗКОВІ ПРАВИЛА
Правило	Що заборонено / що робити натомість
VETO 1: Enum-only callbacks	Всі callback_data та FSM-стани — тільки через constants.js. Магічні рядки заборонені.
VETO 2: NO-TRIM	Не trim() user input у FSM-потоках без явної потреби
VETO 3: Scope модулів	medicalFilter.js тільки фільтрація; planGenerator.js тільки генерація. Без змішування логіки.
VETO 4: Схема БД	Не відхилятись від SQL еталону без окремої іменованої міграції
VETO 5: Error handling	try/catch не приховує помилки — логувати у Supabase logs або Railway console
VETO 6: parse_mode	Не використовувати parse_mode: 'Markdown' для динамічного тексту (імена, дати)
VETO 7: AI безпека	AI не генерує sets/reps/rest та не змінює медичні фільтри — тільки коментарі

13. EDGE CASES ТА ОБМЕЖЕННЯ
12.1 Медичні edge cases
•	Учень без медичних станів → всі вправи NEUTRAL, стандартний відбір
•	Всі вправи для групи м'язів BLOCKED → показати alternatives, попередити тренера
•	Вагітність trimester3 → заборонити full body з вагою, тільки низька інтенсивність
•	MC017 uncontrolled → виключити важкі ваги та вправи на висоті
•	Зміна severity при активному плані → автоматичний перегляд + сповіщення тренеру

12.2 Технічні edge cases
•	Запрошені учні (INVITE_xxx) — при активації інвайту replaceInviteWithChatId оновлює bot_training_data
•	Timeout generateTrainingPlan: якщо > 30 сек → повернути помилку, не зберігати частковий план
•	Дублікат активного плану: при PLAN_ACTIVATE — автоматично деактивувати попередній
•	Відсутній exercise_library.id у БД — перевірка перед INSERT, логувати невалідні IDs
•	parse_mode Markdown — ніколи для повідомлень з динамічним текстом (імена учнів, дати, ваги)

12.3 UX edge cases
•	Учень намагається почати тренування без активного плану → запропонувати «Вільне тренування»
•	Тренер переглядає план без учня (шаблон) → заборонити PLAN_ACTIVATE
•	Видалення активного плану → спочатку деактивувати, потім видаляти


14. КЛЮЧОВІ ФУНКЦІЇ — СПЕЦИФІКАЦІЯ
13.1 getSetsRepsRest(goal, level, vid, mc_status)
Повертає об'єкт { sets, reps, rest_sec } на основі комбінації параметрів. Ізольована функція — не залежить від State або Telegram API.

getSetsRepsRest('lose', 'beginner', 'Базова', 'NEUTRAL')
// → { sets: 3, reps: '15-20', rest_sec: 60 }

getSetsRepsRest('gain', 'advanced', 'Базова', 'ALLOWED_WITH_MOD')
// → { sets: 4, reps: '6-10', rest_sec: 90 }  // mc обмежує: sets-1

13.2 filterExerciseForUser(exercise, userMedConditions)
Детермінований алгоритм, чистая функція. Не звертається до БД. Обробляє medical_contraindications, medical_limitations, safe_for з exercise_library.

13.3 generateTrainingPlan(studentChatId, options)
Оркеструє весь pipeline: читання профілю → параметри → підбір вправ → sets/reps → запис у БД. Async, обгорнути у try/catch. Логувати помилку з plan_id якщо є.

13.4 updatePlanExerciseTargetWeight(planExerciseId, newWeight)
Оновлення target_weight після автопрогресії. UPDATE training_plan_exercises WHERE id = planExerciseId.


15. ЧЕКЛИСТ ТЕСТУВАННЯ
14.1 Медичний профіль
•	Додати MC001 severity=mild → запис у user_medical_conditions
•	Спробувати додати MC001 ще раз → UPDATE severity, не дублікат
•	Видалити стан → is_active = false, не DELETE
•	Переглянути картку вправи після додавання MC → правильний статус (BLOCKED/MOD/SAFE)

14.2 Авто-генерація
•	Beginner 3 дні, lose, без MC → Full Body ×3, вправи 5–6/день, 3 підходи 15–20 повт
•	Intermediate 4 дні, gain, MC001 mild → Upper/Lower, присідання з ⚠️, notes = modifications
•	Advanced 5 днів, keep, MC003 severe → Push/Pull/Legs/Upper/Lower, жими НАД головою відсутні
•	Gender=female, beginner, lose → Full Body з акцентом Ноги/Сідниці
•	MC018 class2 → відсутні вправи стоячи з штангою

14.3 Ручний план
•	Тренер додає вправу з BLOCKED → не з'являється у списку вибору
•	Вибір типу SET → правильні sets/reps/rest
•	Вибір типу SINGLE → sets=1, reps='1', rest=0
•	Активувати план → попередній деактивується, учень отримує повідомлення

14.4 Виконання плану
•	Учень виконав всі підходи → target_weight + 2.5 кг наступного разу
•	Учень 2 рази поспіль не виконав норму → −10% + сповіщення тренеру
•	Зміна severity MC001 → перевірка плану → якщо нова BLOCKED → сповіщення тренеру

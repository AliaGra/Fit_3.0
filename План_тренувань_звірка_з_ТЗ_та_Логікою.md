## 2. Протиріччя (код суперечить ТЗ або Логіці)

### 2.1. VETO 6 — parse_mode для динамічного тексту

**ТЗ розд. 11 (VETO 6):** «Не використовувати parse_mode: 'Markdown' для динамічного тексту (імена, дати)».

**Код:**
- `lib/planRevisionReminders.js`: повідомлення тренеру з `parse_mode: 'Markdown'` і підстановкою **studentName** (динамічне).
- `lib/training.js` (деавтоматизація): повідомлення тренеру з `parse_mode: 'Markdown'` і **studentName** + назва вправи (динамічне).

**Що змінити:** прибрати `parse_mode: 'Markdown'` у цих повідомленнях або не включати в них динамічні частини у форматуванні Markdown (наприклад, не використовувати `**...**` для імені/назви вправи).

---

### 2.2. getSetsRepsRest — сигнатура та врахування MC

**ТЗ розд. 14.1:**  
`getSetsRepsRest(goal, level, vid, mc_status)` — при `ALLOWED_WITH_MOD` передбачається зменшення sets (наприклад sets−1).

**Код:**  
`getSetsRepsRest(goal, level)` — лише два аргументи, врахування vid і mc_status відсутнє.

**Що змінити:** або розширити сигнатуру та логіку (vid, mc_status) згідно з ТЗ, або явно зафіксувати у ТЗ/Логіці поточну спрощену поведінку.

## 3. Що ще потрібно впровадити

### 3.1. Авто-ревізія плану (Логіка 9.4.3–9.4.4, ТЗ 9.3–9.4)

- **generatePlanRevision(plan_id)** у коді відсутня.  
  Потрібно: читати поточний план і вправи, розділяти базові/ізоляційні (за vid), залишати базові, замінювати 30–50 % ізоляційних (з exercise_library за тією ж group_level2, filterExerciseForUser), створювати новий план (generation_type = 'auto_revision', parent_plan_id = старий), записувати вправи (target_weight = NULL для нових), активувати новий, деактивувати старий, лог у plan_adjustments.

- **Cron ревізії** не розрізняє режими:
  - `getPlansDueForRevision()` не повертає **generation_type**.
  - Для **generation_type = 'auto'**: викликати `generatePlanRevision(planId)`, сповістити учня («Твій план оновлено! Ось нові вправи на наступні N тижнів 💪»), позначити нагадування надісланим.
  - Для **generation_type = 'manual'**: лишати поточну поведінку (лише сповіщення тренеру).

**Що зробити:** додати в select у `getPlansDueForRevision` поле `generation_type`; у `planRevisionReminders.js` гілку за `generation_type` (auto → generatePlanRevision + повідомлення учню, manual → як зараз).

---

### 3.2. Запис у plan_adjustments (Логіка 9.3, 9.4.4; ТЗ 8.4, 9.4)

- Таблиця **plan_adjustments** створена міграцією, але у **supabase.js** немає функції запису (на кшталт `insertPlanAdjustment`).
- При ревізії плану та при зміні медичного стану (див. нижче) потрібно писати запис у plan_adjustments (plan_id, new_plan_id за потреби, adjustment_type, details).

**Що зробити:** реалізувати `insertPlanAdjustment(record)` у supabase і викликати її після успішної авто-ревізії та при зміні MC (п. 3.5).

---

### 3.3. Обмеження прогресії при MC (Логіка 9.2, ТЗ 8.4)

- **ALLOWED_WITH_MOD:** прогресія лише через reps, не через weight.
- **severity = moderate:** ліміт ваги = поточна вага × 1.5.
- При загостренні (зміна severity) — деактивація плану + сповіщення тренеру.

У **applyProgressionAfterWorkout** (training.js) medical_status вправи та severity не перевіряються: вага збільшується незалежно від ALLOWED_WITH_MOD і без обмеження 1.5×.

**Що зробити:** у applyProgressionAfterWorkout перед оновленням target_weight: для вправ з medical_status = 'ALLOWED_WITH_MOD' не збільшувати вагу (лише reps, якщо це підтримується); для moderate — не піднімати target_weight вище поточного × 1.5.

---

### 3.4. Оновлення плану при зміні медичного стану (Логіка 9.3, ТЗ 8.4)

- При зміні severity (або додаванні MC) перевірити активний план учня: для кожної вправи викликати **filterExerciseForUser** з оновленими умовами.
- Якщо з’явилась **BLOCKED** — замінити вправу на alternatives або деактивувати план і сповістити тренера.
- Зміни логувати в **plan_adjustments**.

У **medicalProfile.js** (або місці збереження user_medical_conditions) такої перевірки активного плану та запису в plan_adjustments немає.

**Що зробити:** після оновлення/додавання стану в user_medical_conditions для цього chat_id: отримати активний план, для кожної вправи плану викликати filterExerciseForUser; при BLOCKED — або заміна з alternatives, або деактивація плану + сповіщення тренеру; виклик `insertPlanAdjustment` з adjustment_type на кшталт 'mc_change'.

---

### 3.5. Поле revision_weeks у UI (Логіка 9.4.3, ТЗ 9.3)

- Тренер має мати можливість задати **revision_weeks** вручну при створенні плану; дефолт за рівнем підставляється автоматично.

Зараз при створенні плану (ручний і авто) revision_weeks у UI не задається і не передається явно з клієнта — використовується лише дефолт за рівнем при insert.

**Що зробити:** у flow створення плану (trainingPlan.js) додати крок або поле для введення/вибору revision_weeks (опційно), передавати його в insertTrainingPlan; при активації вже використовується revision_weeks із плану.

---

### 3.6. Кількість вправ за таблицею 4.4 (Логіка 4.4)

- Діапазони: Full Body 5–6 / 6–7 / 7–8 (beginner / intermediate / advanced), Upper/Lower 4–5 / 5–6 / 6–7, Push/Pull/Legs 5–6 / 6–8.

У **getSplitSchemeAndDays** для днів задані фіксовані значення **exerciseCount** (наприклад 5 або 6), без діапазону за рівнем.

**Що зробити:** задавати exerciseCount у діапазоні з таблиці 4.4 (наприклад випадкове в межах min–max або вибране правило за рівнем).

### 3.7. MC018 — окрема логіка підбору (Логіка 5.4, ТЗ 6.6)

- class1 (BMI 30–35): уникати важких присідань з вагою; leg press, жим ногами.
- class2 (BMI 35–40): виключити вправи стоячи з штангою; перевага тренажери/кабелі.
- class3 (BMI 40+): тільки сидячи/лежачи, без стрибків.

У **pickExercisesForDay** та медичному фільтрі окремої логіки для MC018 і класів ожиріння (тип інвентаря, положення) немає.

**Що зробити:** при наявності MC018 у user_medical_conditions визначити клас (за BMI з профілю або severity); у підборі вправ виключати/пріоритизувати вправи згідно з правилами п. 5.4 (можливо потрібні додаткові поля або теги в exercise_library).

---

### 3.8. Female — важка вага для грудей (Логіка 5.3)

- «Виключити вправи на важку вагу для грудей за замовчуванням, якщо немає goal = gain».

У **pickExercisesForDay** для gender = female це не враховано (немає фільтра за типом навантаження для грудей при goal ≠ gain).

**Що зробити:** при female і goal !== 'gain' у логіці підбору вправ для грудей виключати або понижувати пріоритет вправ «важка вага» (якщо є відповідне позначення в бібліотеці).

---

### 3.9. Fallback при малому пулі після Anti-Repeat (ТЗ 6.7)

- «Якщо після застосування правил А+Б пул став меншим за потрібну кількість вправ → знімати обмеження Б (між планами) і логувати. Правило А не знімається.»

У коді при малому пулі є лише fallback до shuffle для вибору; обмеження Б (previousPlanIsolationIds) не знімається з логуванням.

**Що зробити:** якщо після фільтрації за А і Б allowed.length < dayConfig.exerciseCount, повторити підбір без виключення за previousPlanIsolationIds (або з порожнім цим набором) і залоговати факт зняття обмеження Б.

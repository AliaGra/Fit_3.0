## 📌 ПЕРЕНЕСЕННЯ В GAS (DEPLOY CHECKLIST)

**Симптоми після поетапного переносу модулів:**
- Тільки Helpers завантажено → бот не реагує на /start (немає doPost/route або TELEGRAM_API_URL).
- Після User, Menu, State → привітання з’являється, але натискання кнопки не обробляється; кожні 4–6 хв повторно приходить привітання.

**Мінімальний набір модулів для роботи /start та кнопок:**
1. **constants** (першим: BOT_TOKEN, TELEGRAM_API_URL, CONSTANTS, parseCallbackData)
2. **Main** (doPost, дедуплікація)
3. **Helpers** (extractMessage, safeSend, sendKeyboard, answerCallback, callTelegramAPI_)
4. **State** (State.get/set/clear/update/getSafe)
5. **Router** (route, handleTextMessage_, handleCallback_)
6. **User** (getByChatId, createUser)
7. **Menu** (show)
8. **Registration** (start, handleCallback, handleTextMessage)

**Обов’язково в Script Properties:** `BOT_TOKEN`, `SPREADSHEET_ID`. Без BOT_TOKEN бот не відправить жодного повідомлення.

**Workaround повторного привітання (retry Telegram):** у Main.gs застосовано атомарну дедуплікацію через LockService: при retry того ж update_id лише один doPost обробляє update, інші одразу повертають 200. Додатково в Registration.start — throttle дубля: не надсилати привітання тому ж chatId протягом 2 хв (CacheService WELCOME_&lt;chatId&gt;).

**Якщо привітання повторюється через 1–5 хв:** виконати в GAS Run → `listAllTriggers` (переглянути список), потім Run → **`deleteAllTimeTriggers`** — видаляє всі тригери по часу (CLOCK), які найчастіше викликають повторні привітання. Додатково throttle у Registration.start — 15 хв (900 с).

**Якщо бот не реагує на кнопки (Нова реєстрація / У мене є код):** переконатися, що webhook приймає callback_query: у GAS Run → `setWebhook()` (в коді вже вказано `allowed_updates: ['message', 'callback_query']`). Перевірити Run → `getWebhookInfo()` — у відповіді не має бути last_error_message; pending_update_count переглянути.

**Помилка "Wrong response from the webhook: 302 Moved Temporarily":** Telegram не слідує за редіректами. Webhook має одразу повертати 200 OK з того самого URL. Можливі причини: (A) В setWebhook передано URL, який редіректить (наприклад /dev). **Рішення:** URL з Керування розгортаннями (закінчується на /exec), WEB_APP_URL у Script Properties, Run → setWebhook. (B) **Доступ до Web App не "Усі"** — якщо при розгортанні вказано "Тільки я" (Only myself), запити від Telegram редіректуються на сторінку входу Google → 302. **Рішення:** Розгортання → Керування розгортаннями → олівець (редагувати) → **Доступ: Усі** (Who has access: Anyone) → Зберегти версію. Потім знову Run → setWebhook. Після виправлення doPost перестане викликатися кожну секунду, callback_query почне доставлятися.

**Якщо /exec дає 302, а script.googleusercontent.com дає 405:** це обмеження для Telegram (редіректи заборонені). Робочий варіант — **proxy**. Дивись файл `cloudflare-worker.js` (запускає Worker, що приймає Telegram POST і пересилає на /exec з follow redirects). У GAS додано `setWebhookViaProxy` — потрібно записати PROXY_URL у Script Properties і викликати цю функцію.

**Де дивитися логи doPost (виконання веб-застосунку):** У GAS: Виконання (Executions) → у списку клік по **рядку** потрібного виконання doPost (не по назві функції). Відкривається деталі виконання; там — логи. Якщо рядок не розкривається: спробувати клік по даті/часу або по іконці зліва. У новому інтерфейсі: вибрати виконання → знизу або справа з’являються логи. Якщо логів не видно — переконатися, що в коді є Logger.log (у Main.doPost вони є при callback_query та при помилці).

## 🚨 КРИТИЧНІ ПРОБЛЕМНІ ЗОНИ (KNOWN ISSUES)

### **1. ПАДІННЯ ПРИ РЕЄСТРАЦІЇ ("Falling Problem")**

**Локація:** `Registration.handleMessage()` → `finishRegistration_()`

**Симптоми:**
```
Користувач вводить ім'я → "Олексій"
↓
Бот відповідає: "Приємно, Олексій! Що робимо далі?"
↓ [Користувач натискає кнопку]
БОТ ЗНОВУ ВІДПРАВЛЯЄ: "Привіт! 👋 Вітаю в системі FIT 3.0"
↓
ЦИКЛІЧНЕ ПОВТОРЕННЯ welcome message
```

**Root Cause:**
```
┌─────────────────────────────────────────────────────────┐
│ ПРОБЛЕМА 1: Race Condition в State                      │
│                                                          │
│ handleMessage() встановлює:                             │
│   State.set({ firstName: "Олексій", ... })             │
│                                                          │
│ НО callback приходить РАНІШЕ, ніж State збережено       │
│ handleCallback() читає State → null або старий стан     │
│                                                          │
│ РЕЗУЛЬТАТ: Router вважає, що користувач не зареєстрован │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│ ПРОБЛЕМА 2: Повільний PropertiesService                │
│                                                          │
│ State.set() → PropertiesService.setProperty()           │
│   ↓ ЗАТРИМКА: 200-500ms                                │
│                                                          │
│ Якщо користувач натискає кнопку протягом 500ms →       │
│ State.get() повертає старе значення                     │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│ ПРОБЛЕМА 3: Sheets.insertUser() теж повільний          │
│                                                          │
│ finishRegistration_() викликає User.createUser()        │
│   ↓ Sheets.insertUser()                                │
│     ↓ appendRow() → 1000-3000ms                        │
│                                                          │
│ За цей час може прийти ще один update від Telegram     │
└─────────────────────────────────────────────────────────┘
```

**Як відтворити:**
```
1. Почати реєстрацію
2. Ввести ім'я
3. ШВИДКО натиснути кнопку (< 500ms після введення)
4. Спостерігати падіння
```

**Тимчасове рішення (workaround):**
```javascript
// В Router.handleCallback_()
function handleCallback_(chatId, data, callbackQueryId) {
  // CRITICAL FIX: Затримка перед перевіркою State
  Utilities.sleep(300); // Даємо час PropertiesService
  
  var state = State.get(chatId);
  // ...
}
```

**Довгострокове рішення:**
```
1. Міграція State на MemoryCache (швидший доступ)
2. Використання Lock Service для синхронізації
3. Дедуплікація update_id від Telegram
```

### **3. CALLBACK НЕ РОЗПІЗНАЄТЬСЯ (Router Mismatch)**

**Локація:** `Router.handleCallback_()` → Registration/Profile/Training

**Симптоми:**
```
Користувач натискає кнопку [Чоловік 👨]
↓
data = "male"
↓
Router НЕ знає куди направити
↓
Fallback: Menu.show() (неправильно)
```

**Root Cause:**
```
┌─────────────────────────────────────────────────────────┐
│ ПРОБЛЕМА: SMART ROUTING з конфліктами                   │
│                                                          │
│ Callback "male" може означати:                          │
│ - Вибір статі в реєстрації (Registration)              │
│ - Вибір статі в профілі (Profile)                      │
│                                                          │
│ Router не знає контекст без State!                     │
└─────────────────────────────────────────────────────────┘
```

**Код проблеми:**
```javascript
// Router.handleCallback_()
if (data === CONSTANTS.GENDER.MALE || data === CONSTANTS.GENDER.FEMALE) {
  // ❌ НЕ ЗНАЄМО контекст!
  // Це Registration чи Profile?
  Registration.handleCallback(chatId, data); // Припущення
}
```

**Правильне рішення (вже впроваджено в vs9.0):**
```javascript
// SMART ROUTING з перевіркою State
if (data === CONSTANTS.GENDER.MALE || data === CONSTANTS.GENDER.FEMALE) {
  var state = State.get(chatId);
  
  if (state && state.step === 'profile_edit_gender') {
    Profile.handleCallback(chatId, data);
    return;
  }
  
  // Інакше - реєстрація
  Registration.handleCallback(chatId, data);
  return;
}
```

### **4. ІНВАЙТ КОД КОНФЛІКТ (Duplicate Invite)**

**Симптоми:**
```
Тренер 1 створює інвайт → INVITE_A3F7
Тренер 2 (через мілісекунди) створює інвайт → INVITE_A3F7 (той самий!)
↓
КОНФЛІКТ: Два учні з одним кодом
```

**Root Cause:**
```
┌─────────────────────────────────────────────────────────┐
│ Utilities.getUuid().split('-')[0] НЕ гарантує унікальн. │
│                                                          │
│ UUID: "a3f7c2d1-8e4b-4f3a-9d6e-1b5c8a2f7e9d"           │
│         ^^^^^^^^ ← Беремо тільки перші 8 символів       │
│                                                          │
│ Колізія можлива при ~65536 комбінаціях (16^8)          │
└─────────────────────────────────────────────────────────┘
```

**Рішення:**
```javascript
function createPlaceholderUser(coachId, studentData) {
  var attempts = 0;
  var inviteCode;
  
  do {
    var uniqueSuffix = Utilities.getUuid().split('-')[0].toUpperCase();
    inviteCode = 'INVITE_' + uniqueSuffix;
    
    // Перевірка на існування
    var existing = Sheets.findUserByInviteCode(inviteCode);
    if (!existing) break;
    
    attempts++;
  } while (attempts < 5);
  
  if (attempts === 5) {
    throw new Error('Cannot generate unique invite code');
  }
  
  // Продовжити створення...
}
```

## ⚡ RACE CONDITIONS (Паралельні запити)

### **RACE 1: Два update від Telegram одночасно**

**Сценарій:**
```
Користувач швидко двічі натискає одну кнопку
↓
Telegram надсилає 2 update:
  - update_id: 12345
  - update_id: 12346
↓
Google Apps Script отримує ОБА запити паралельно
↓
Два виклики doPost() одночасно
```

**Що може статися:**
```
doPost #1:                      doPost #2:
  State.get() → { step: 'A' }     State.get() → { step: 'A' }
  ↓                               ↓
  Обробка...                      Обробка...
  ↓                               ↓
  State.set({ step: 'B' })        State.set({ step: 'C' })
                                  ↑
                    Перезаписує результат #1!
```

**Рішення (Lock Service):**
```javascript
function route(update) {
  var lock = LockService.getScriptLock();
  
  try {
    // Чекаємо 10 сек на отримання lock
    lock.waitLock(10000);
    
    var msg = Helpers.extractMessage(update);
    // Обробка...
    
  } catch (e) {
    console.error("Lock timeout: " + e.message);
  } finally {
    lock.releaseLock();
  }
}
```

### **RACE 2: State.update() під час паралельних запитів**

**Сценарій:**
```
Request #1: State.update({ firstName: "Олексій" })
Request #2: State.update({ lastName: "Петренко" })
↓
Обидва читають State → { }
↓
Request #1 записує: { firstName: "Олексій" }
Request #2 записує: { lastName: "Петренко" }
↑
firstName ВТРАЧЕНО!
```

**Root Cause:**
```javascript
function update(chatId, newParams) {
  var currentState = get(chatId) || {}; // ⚠️ Read
  
  for (var key in newParams) {
    currentState[key] = newParams[key]; // ⚠️ Modify
  }
  
  set(chatId, currentState); // ⚠️ Write
}
```

**Рішення:** Використовувати Lock Service (див. вище)

### **DATA 3: Формат дати в Sheets**

**Проблема:**
```
JavaScript Date → Sheets:
new Date() → "Thu Jan 31 2026 15:30:00 GMT+0200"

При читанні назад:
getValues()[0][0] → може бути Date object АБО строка
```

```javascript
function mapRowToUser(row) {

  } else if (typeof createdAt === 'string') {
    createdAt = new Date(createdAt);
  } else {
    createdAt = new Date(); // Fallback
  }
  
  return {
    createdAt: createdAt,
    // ...
  };
}
```
